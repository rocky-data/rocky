A Rocky run emits OpenTelemetry traces and metrics, writes structured logs to stderr, and keeps a local record of every log event on disk. Point the exporter at a collector, or read the local files.

Terms: a **span** is a timed record of one piece of work. A **trace** is all the spans of one operation, linked parent to child; its outermost span is the **trace root**. **OTLP** is the OpenTelemetry wire format. A **collector** receives it and forwards it to a backend such as Grafana Tempo. Rocky's **exporter** sends the data.

## What Rocky emits

- **Traces**: spans for the phases of a run, over OTLP gRPC.
- **Metrics**: run counters and duration histograms, over OTLP.
- **Structured logs**: events on stderr, as JSON (one object per line) when producing JSON output, compact human-readable otherwise.
- **Local trace files**: each log event with its span chain, as JSONL under `.rocky/traces/`.

OTLP is opt-in through one environment variable. Logs and local trace files are always on.

### Spans

| Span | Emitted by | What it covers |
|---|---|---|
| `run` | `rocky run` | The whole run, carrying `run_id`. The trace root unless an upstream context was supplied. |
| `discover_sources` | source discovery | Resolving sources before planning. Parents the discovery work. |
| `materialize.table` | model execution | One model, carrying `rocky.model.fqn` and `rocky.model.kind`. |
| `statement.execute` | warehouse adapter | One SQL statement. |
| `state.download` / `state.upload` / `state.probe` | object-store state sync | Remote state reads and writes, carrying `backend` and `bucket`. |
| `scheduler.tick` | resident scheduler | One reconciliation pass of `rocky serve --scheduler` (experimental), carrying `rocky.scheduler.outcome` and the due/executed/failed/skipped counts. |

```
 scheduler.tick               ← its own trace root, from
  │                             rocky serve --scheduler (experimental)
  │ hands TRACEPARENT to the run it launches
  ▼
 run                          ← the trace root of a plain rocky run
  ├── discover_sources
  └── materialize.table       ← one span per model
       └── statement.execute  ← one per SQL statement, warehouse
                                adapters only
```

Limits:

- **`statement.execute` comes from warehouse adapters.** Databricks, Snowflake, BigQuery and Trino emit it. PostgreSQL, Redshift, ClickHouse, SQL Server, Spark and embedded DuckDB do not, so a DuckDB run shows model spans only. The `rocky.adapter.name`, `rocky.statement.kind` and `rocky.warehouse.name` attributes ride on the Databricks, Snowflake and BigQuery spans. Trino emits a simpler span plus `statement.execute_arrow` on its Arrow path.
- **`scheduler.tick` records its outcome and counts on every pass**, even when nothing ran, so an idle loop and a wedged one differ in the trace.
- **`rocky.query_duration_ms` is populated by the Databricks adapter only.**
- **`governance_setup` and `batched_checks` are marker spans.** They do not parent the events of their phases, which stay at the trace root.

### Connected traces

Rocky reads and passes the W3C trace context through the `TRACEPARENT` environment variable.

- **Inbound.** With `TRACEPARENT` set, the root spans the process opens become children of the span it names. This is how `rocky serve --scheduler` connects to what it runs: each `scheduler.tick` hands the value to the `rocky run` child, whose `run` span lands under the tick. A CI job, wrapper or orchestrator that exports `TRACEPARENT` gets Rocky's spans nested under its own.
- **Any invocation is affected.** Every Rocky command launched with `TRACEPARENT` exported (`run`, `compile`, `plan`, ...) roots under it. Unset it for an independent trace. `rocky run --watch` holds the parent it started with, so every iteration lands in one trace.
- **In-process background work opens its own trace**: the scheduler's loop, the periodic state uploader and the replication path's per-table spans.
- **Subprocesses inherit it.** A job submitted to `rocky serve` runs in a child `rocky run`, so **every job a server runs joins the trace the server was launched with**. Unset the variable for the server process for independent job traces.
- **Sampling is `ParentBased(AlwaysOn)`.** A `TRACEPARENT` ending in `-00` (not sampled) drops the `run` span and everything under it. Self-rooting spans, such as per-table spans on a replication run, still export. The run executes normally.
- **A malformed value is ignored.** The process roots its own trace.
- **The Dagster integration does not set `TRACEPARENT`.** A Dagster-launched run joins Dagster's trace only if something upstream exports it.

Without `OTEL_EXPORTER_OTLP_ENDPOINT` there is no exporter, so nothing is emitted.

### Metrics

Rocky records metrics in-process and flushes them as the run exits. Counters go out as gauges (the last value over the run). Durations go out as histograms.

| Metric | Type | Meaning |
|---|---|---|
| `rocky.tables_processed` | gauge | tables materialized in the run |
| `rocky.tables_failed` | gauge | tables that failed |
| `rocky.statements_executed` | gauge | SQL statements executed |
| `rocky.retries_attempted` | gauge | retries attempted |
| `rocky.retries_succeeded` | gauge | retries that recovered |
| `rocky.anomalies_detected` | gauge | anomalies flagged by checks |
| `rocky.error_rate_pct` | gauge | failed tables as a percentage |
| `rocky.table_duration_ms` | histogram | per-table materialization time, in milliseconds |
| `rocky.query_duration_ms` | histogram | per-statement warehouse time, in milliseconds |

Instrumentation is adapter- and pipeline-specific. Databricks emits `rocky.statements_executed`. Databricks and BigQuery emit the retry counters. Replication runs emit `rocky.tables_processed`, `rocky.tables_failed` and `rocky.table_duration_ms`. A missing metric means that path is not instrumented, not that nothing happened.

#### Resident scheduler metrics

`rocky serve --scheduler` (experimental) exports these for the life of the process. They are monotonic counters: read them with `rate()`. They appear only while the scheduler runs.

| Metric | Type | Meaning |
|---|---|---|
| `rocky.scheduler.ticks` | counter | reconciliation passes, split by `outcome` |
| `rocky.scheduler.due` | counter | demands that came due |
| `rocky.scheduler.executed` | counter | demands that ran to a terminal outcome |
| `rocky.scheduler.skipped` | counter | demands suppressed, split by `reason` |
| `rocky.scheduler.lag_seconds` | histogram | seconds between a demand's logical time and its execution |
| `rocky.scheduler.consecutive_failures` | gauge | consecutive failed runs, per `pipeline` |

`outcome` is one of `completed`, `config_error`, `permit_held`, `lock_skipped`, `fault`, `spool_unreadable`. `spool_unreadable` is a tick that ran its schedules but could not read the webhook spool, so it consumed no webhook demand. It is not `completed`, and the shipped Grafana rules alert on it. Summed across outcomes, `ticks` is the liveness signal. Split by outcome, it shows a scheduler that ticks but fails to parse `rocky.toml` (`outcome=config_error`).

`reason` is one of `not_due`, `disabled`, `paused`, `in_flight`, `catchup_skipped`, `failure_backoff`, `partial_backoff`, `freeze_hold`, `dedup`, `config_error`, `history_unavailable`, `state_busy`, `spool_unreadable`. The last is one skip per tick for the whole webhook source, the same entry `rocky tick --output json` lists. The `pipeline` label is a configured name, so neither label grows unbounded.

`rocky.scheduler.consecutive_failures` resets on restart, and a pipeline removed from config leaves a stale series. Alert on it together with a freshness check.

### Structured logs

stdout stays reserved for the `--output json` result of `discover`, `plan` and `run`. The active `run` span carries `run_id`, the id in `rocky history` and `rocky trace`.

```json
{"timestamp":"2026-07-17T09:14:22.481Z","level":"INFO","fields":{"message":"idempotency key claimed — proceeding","backend":"local"},"span":{"run_id":"run-20260717-091422-481","name":"run"},"target":"rocky::run"}
```

`RUST_LOG` sets verbosity. The default keeps Rocky's spans at `info` and quiets the query-cache trace:

```bash
RUST_LOG=info rocky -c rocky.toml run
```

### Local trace files

Rocky writes one JSONL file per process under `.rocky/traces/`, named `{timestamp}-{pid}.jsonl`. Each line is a log event with timestamp, level, target, fields and span chain. No configuration is needed.

- The last 20 files are kept. Set `ROCKY_TRACE_RETAIN_RUNS` to change that.
- Set `ROCKY_TRACE_DISABLE=1` to turn the files off.

`rocky trace` and `rocky replay` render a run's timeline from the persisted run record in the state store, not from these files.

## Turning on OTLP export

Export starts when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. It switches on traces and metrics together. When unset, Rocky never builds the exporter.

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_SERVICE_NAME=rocky   # optional; defaults to "rocky"
rocky -c rocky.toml run
```

- `OTEL_EXPORTER_OTLP_ENDPOINT` is the collector's gRPC endpoint. Use `http://`: the exporter does not use TLS. An `https://` URL, or a bare `host:port` (read as `https://`), logs a warning at start-up and exports nothing. `OTEL_EXPORTER_OTLP_INSECURE=true` reads a bare `host:port` as `http://`.
- `OTEL_SERVICE_NAME` sets `service.name`, the attribute to filter on in the backend.

If the endpoint is unreachable, Rocky warns and keeps running. Each send is tried once. Export never fails a run. It needs a release built with the OpenTelemetry exporter: see the CHANGELOG for the release that adds it.

## A local Grafana stack

[`deploy/observability/`](https://github.com/rocky-data/rocky/tree/main/deploy/observability) ships a single-node development stack: Grafana, Alloy, Tempo, Loki and Prometheus. It is not a hardened production deployment.

```bash
# 1. Start the stack (from deploy/observability/).
docker compose up -d

# 2. Run a pipeline with export pointed at Alloy's OTLP receiver.
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 \
OTEL_SERVICE_NAME=rocky \
  rocky -c rocky.toml run

# 3. Open Grafana at http://localhost:3000.
```

In Grafana, search the Tempo data source for traces where `service.name` is `rocky`. Two dashboards are provisioned: **Rocky Runs** (tables processed and failed, error rate, duration histograms) and **Rocky Scheduler** (lag, due/executed/skipped-by-reason counts, per-pipeline consecutive failures; it fills once `rocky serve --scheduler` exports). Ports and commands are in the `deploy/observability/` README.

## Collecting the structured logs

To get the JSON logs into the same place, capture stderr to a file, tail it with Alloy, and lift `run_id` into a label:

```bash
rocky -c rocky.toml run 2>> /var/log/rocky/run.jsonl
```

```
local.file_match "rocky_logs" {
  path_targets = [{ __path__ = "/var/log/rocky/*.jsonl" }]
}

loki.source.file "rocky_logs" {
  targets    = local.file_match.rocky_logs.targets
  forward_to = [loki.process.rocky.receiver]
}

loki.process "rocky" {
  stage.json {
    expressions = { run_id = "span.run_id" }
  }
  stage.labels {
    values = { run_id = "" }
  }
  forward_to = [loki.write.default.receiver]
}

loki.write "default" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}
```

Events inside a run carry the `run_id` label in Loki, so you can filter by it and cross-reference the run's record. Events outside the run span, such as early start-up lines, carry no label.
