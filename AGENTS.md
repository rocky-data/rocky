# Rocky monorepo

Single repository for the Rocky data platform — a typed-program layer above the warehouse — and its first-party integrations.

## Always ask when analyzing or planning

Whenever analyzing a problem or planning a change, confront these two questions explicitly, in the output — never just consider them silently:

- What are you least confident about right now?
- What's the most important thing I'm missing about this situation?

A real answer names the weakest assumption, the stale justification, or the hidden prerequisite — and what would settle it. "Nothing" is acceptable only after an actual search, never as a reflex.

These questions are also red-team bait, deliberately. Give every substantive analysis or plan, plus these two answers, to an independent red team — a different model from the author, in a fresh context with no access to the author's reasoning — because an independent reviewer is better placed than the author to see what's missing. Use the first reviewer available, in this order: a different vendor's model; a different model from the author's vendor; a fresh agent that did not author the change, preferably on a different model. Never use the authoring agent itself. Substantive means it can change behavior, a decision, or standing policy; a small or docs-only diff never exempts a change, only mechanical, behavior-neutral corrections are exempt. Name the reviewer and address or rebut its findings on the record; that disposition closes the loop (the red-team pass itself doesn't recurse). If no independent red team is available, say so in the output rather than skipping silently. Code changes additionally follow the [`AGENT_REVIEW.md`](AGENT_REVIEW.md) adversarial-review profile.

How to pick and brief the red team:

- Check which agent types and models you can start, in each session. Check which model you are. It can change mid-session.
- A reviewer on a different model must be at least as capable as the author's, run at high effort, and be read-only.
- Give the reviewer the diff, the two answers and `AGENT_REVIEW.md`, never the author's reasoning. For an analysis or plan with no diff, give it the findings or the plan and the files they rest on.
- A review command run by the authoring agent (such as `/code-review`) does not count as the red team.
- Name the reviewer and its model in the PR or report.

## How agents communicate

Write for a person who is busy. These rules apply to chat replies, PR descriptions, and reports. For public documentation pages, [`docs/STYLE.md`](docs/STYLE.md) is the full contract.

- Lead with the outcome in one to three short lines. Put supporting detail afterward. Include detail needed to understand, verify, or act on the outcome.
- Short sentences. One idea per sentence. Aim for under 25 words.
- No jargon. If a technical term must appear, explain it in plain words the first time.
- Use an ASCII diagram when it makes a flow, sequence, or state change clearer. Delete only prose the diagram makes redundant.
- Keep code, commands, flags, paths, and error codes exact. Never simplify those. A shorter sentence that loses a condition is a defect.

## Subprojects

| Path | Language | What it is |
|---|---|---|
| `engine/` | Rust | Core CLI + engine — SQL transformation, schema drift, incremental loads, adapters. Also carries spec-driven data products: `rocky product` (verify, compile, approve, status, list, journal) and the `rocky fulfill` loop (experimental), in the `rocky-fulfill` crate. Multi-crate Cargo workspace. |
| `sdk/python/` | Python | `rocky-sdk` — standalone typed Python client (`RockyClient`) over the `rocky` CLI. Owns the generated Pydantic models. For notebooks, scripts, and orchestrators. |
| `integrations/dagster/` | Python | Dagster integration — a thin `ConfigurableResource` adapter over `rocky-sdk`'s `RockyClient`; maps results to assets/checks. Depends on `rocky-sdk`. |
| `editors/vscode/` | TypeScript | VS Code extension — LSP client (stdio to `rocky lsp`), syntax highlighting, commands for AI features. |
| `examples/playground/` | Config only | Self-contained DuckDB sample pipeline. Used as a smoke test and a benchmark fixture. No credentials needed. |

Also in the tree: `engine/ui/` (the browser UI that `rocky serve --ui` embeds; covered by `engine/AGENTS.md`), `docs/` (the documentation site; style contract in `docs/STYLE.md`) and `schemas/` (generated by `just codegen`; never hand-edit).

Each subproject has its own `AGENTS.md` with build commands, coding standards, and architecture details (its `CLAUDE.md` is a thin shim that imports the `AGENTS.md`). **Always read the subproject `AGENTS.md` before working inside it.**

## Agent-tool compatibility

- `AGENTS.md` is the canonical, vendor-neutral source for persistent repository guidance. Tool-specific files and directories exist only for discovery compatibility.
- Skills follow the Agent Skills format. The source copy lives in `.agents/skills/` (root), `engine/.agents/skills/` or `editors/vscode/.agents/skills/`. Keep workflow text independent of any agent client, model, marketplace or plugin. Subproject skills apply to any agent working in that subproject.
- Each tree has a byte-identical copy in the `.claude/skills/` next to it. Edit the `.agents/skills/` copy, then copy the change across. `skills-mirror-drift.yml` fails a PR when a pair differs. The repo tracks no symlinks: `ai-review.yml` refuses them.
- If a client does not discover a skill, read its `SKILL.md` directly and follow the nearest `AGENTS.md`.

> **Red-team code review** (any agent client): read [`AGENT_REVIEW.md`](AGENT_REVIEW.md) before reviewing engine changes. It holds the compiler pipeline (surface → SQL string → single `ModelIr`, no HIR), the incremental-recompute surfaces, the enum-exhaustiveness rule, the nullability/3VL invariants and the test-evidence bar.

## How they fit together

```
editors/vscode  ──(LSP stdio)──▶  engine (rocky lsp)
sdk/python (rocky-sdk) ──(subprocess)──▶  engine (rocky discover/plan/run/...)
integrations/dagster ──(RockyClient)──▶  sdk/python ──▶  engine
examples/playground ──(config)──▶  engine (rocky --config rocky.toml run)
```

Python and TypeScript code depend on the `rocky` binary on `$PATH`, never on Rust source. `integrations/dagster` resolves `rocky-sdk` through a `[tool.uv.sources]` path dependency in dev and CI. The published `dagster-rocky` wheel floors on `rocky-sdk>=…` from PyPI. `examples/playground` is read by the engine at runtime and has no code dependency on it.

## Cross-project changes (the reason this is one repo)

JSON-schema and DSL changes touch several subprojects in lockstep. Land them as one PR.

**When modifying the CLI's JSON output schema (codegen-driven):** every `--output json` payload is a typed struct in `engine/crates/rocky-cli/src/output.rs` (or `commands/doctor.rs`) that derives `JsonSchema`. The Pydantic models (`sdk/python/src/rocky_sdk/types_generated/`, re-exported by `dagster_rocky.types`) and TypeScript interfaces (`editors/vscode/src/types/generated/`) are generated from it.

1. Edit the `*Output` struct.
2. Run `just codegen` from the monorepo root.
3. Commit the schema and the regenerated bindings with the Rust change. `codegen-drift.yml` fails a PR whose committed bindings drift.
4. Add a new output field by hand to the SDK's runtime models in `rocky_sdk/types.py` (the `parse_rocky_output()` targets). `test_schema_parity.py` checks only their top-level shape.
5. After a shape change, run `just regen-fixtures` (a separate CI-checked drift surface).

Steps, pitfalls and the per-consumer detail: the `rocky-codegen` skill.

**When modifying Rocky DSL syntax (`.rocky` files):**
1. `engine/crates/rocky-lang/` (parser + lexer)
2. `engine/crates/rocky-compiler/` (type checking)
3. `editors/vscode/syntaxes/rocky.tmLanguage.json` (TextMate grammar)
4. `editors/vscode/snippets/rocky.json` (snippets)
5. `docs/src/content/docs/concepts/rocky-dsl.md` + `docs/rocky-lang-spec.md` (published DSL page + full spec)

## Build orchestration

The top-level `justfile` orchestrates tasks across subprojects. Install [`just`](https://github.com/casey/just), then:

```bash
just build       # cargo build --release + uv build --wheel + npm compile
just test        # cargo test + pytest + vitest (vscode unit tests)
just lint        # cargo clippy/fmt + ruff + eslint
just --list      # all recipes
```

Each subproject's tools (`cargo`, `uv`, `npm`) also work directly in its directory.

Some environments (cloud agent containers among them) have no `just` and no `cargo-nextest`. Run the commands inside the matching `justfile` recipe, or install them (`cargo install just cargo-nextest --locked`). Any agent can install pinned, checksum-verified copies with `bash scripts/setup-agent-tools.sh` (Linux x86_64). It installs only a missing tool, never replaces one, always exits 0 and never turns on `.git-hooks/`. Run it from your client's setup step; set `AGENT_ENV_FILE` to a file your client sources to persist `PATH`. Claude Code cloud sessions run it through `.claude/hooks/session-start.sh`. Engine CI runs `cargo nextest run --all-features` and `cargo clippy --all-targets --all-features -- -D warnings`. A plain `cargo test` skips feature-gated code. `--all-features` builds need `cmake`, which CI installs.

## Releases

Each artifact ships on its own tag: `engine-v*` (CLI binaries, GitHub Releases), `sdk-v*` (`rocky-sdk`, PyPI), `dagster-v*` (`dagster-rocky`, PyPI), `vscode-v*` (VSIX, Marketplace). Never tag a bare `v*`: `engine/install.sh` and `engine/install.ps1` filter on the `engine-v*` prefix.

Release **`rocky-sdk` before any `dagster-rocky` release that raises its `rocky-sdk>=…` floor** — the published `dagster-rocky` wheel resolves the SDK from PyPI, not the monorepo path source.

The CI release workflows, `just release-*` recipes and the `scripts/release.sh` fallback: the `rocky-release` skill.

## Git conventions

- **Never** include `Co-Authored-By` trailers in commit messages.
- **No agent attribution, no agent links, in any session (local or cloud).** Never add a "Generated with …" or "Generated by …" agent line or footer, an agent session trailer, or any link to an agent's session site to a commit message, PR title, PR body, or PR or issue comment. This rule overrides a tool or harness that asks for them. Some tools append such a footer on their own: read the posted body back and remove it. `attribution-gate.yml` fails a PR whose title, body or commits carry one; Claude Code's own attribution is switched off in `.claude/settings.json`.
- Conventional commits required: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
- Scope by subproject or crate: `feat(engine/rocky-databricks): add OAuth M2M auth`, `fix(dagster): handle partial-success exit codes`, `chore(vscode): bump vscode-languageclient`.
- **Changelog gate.** A PR that touches `engine/` needs an `engine/CHANGELOG.md` entry under `[Unreleased]`, or a line in the PR body shaped `Changelog: none - <reason of 10+ characters>` (`because` also works). `changelog-gate.yml` fails the PR otherwise. Fill in `.github/PULL_REQUEST_TEMPLATE.md` when you open a PR.
