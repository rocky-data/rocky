Rocky's engine is a single Cargo workspace. It holds 32 crates under
`engine/crates/`, plus two binary crates. Each crate does one job.

This page is the map of those crates. For the step-by-step walkthrough of a run,
read [Execution Flow](/concepts/execution-flow/).

## How data flows

From config file to warehouse result. [Execution Flow](/concepts/execution-flow/) traces each step.

```
rocky.toml ─► Config ─► DiscoveryAdapter ─► source metadata
                                                  │
   .sql + .toml models ─► rocky-compiler ─► ProjectIr (one ModelIr per model)
                              │ E### / W### diagnostics
                              ▼
        topological sort ─► layers (parallel inside a layer)
                              │ per model: drift ─► skip gate ─► SQL gen ─► execute ─► checks
                              ▼
                       WarehouseAdapter ─► warehouse
                              │
                              ▼
        state store (redb): watermarks, run progress ─► hooks + JSON on stdout
```

## Adapter model

An adapter is the plug between the engine and one outside system. Rocky has two kinds.

**Source adapters** do *discovery*: they find which schemas and tables exist. They do not extract data. An ingestion tool (Fivetran, Airbyte) or a manual load must land the data in the warehouse first.

| Crate | Discovers from |
|---|---|
| `rocky-fivetran` | The Fivetran REST API: connectors and their enabled tables |
| `rocky-airbyte` | The Airbyte API |
| `rocky-iceberg` | An Iceberg REST catalog |
| `rocky-duckdb` | `information_schema` of a local DuckDB database |
| Manual source (in `rocky-core`) | `rocky.toml` |

The Fivetran and Airbyte adapters can wait for a running sync, and can start one when both opt-ins are set (`allow_sync_trigger` on the adapter, `trigger = true` on the pipeline). Rocky still moves no data.

**Warehouse adapters** do *execution*: they run SQL, manage the catalog lifecycle, and apply governance (tags, permissions, workspace isolation).

| Crate | Warehouse |
|---|---|
| `rocky-databricks` | Databricks SQL Statement API, Unity Catalog, adaptive concurrency |
| `rocky-snowflake` | Snowflake REST API |
| `rocky-bigquery` | BigQuery REST API (Beta) |
| `rocky-trino` | Trino `/v1/statement` (Beta) |
| `rocky-postgres` | PostgreSQL and Redshift (Beta), wire protocol |
| `rocky-sqlserver` | SQL Server over TDS. Azure SQL and Fabric Warehouse are Beta |
| `rocky-clickhouse` | ClickHouse HTTP interface (Beta) |
| `rocky-spark` | Apache Spark over Spark Connect (Beta) |
| `rocky-duckdb` | Local in-process execution for development, testing and CI |

Auth, strategies and limits for each warehouse: [Adapters](/reference/configuration/#per-adapter-setup).

**`rocky-ir`** holds the typed Intermediate Representation (IR): `ModelIr`, `MaterializationStrategy`, and the source and target descriptors. It is a separate crate so an adapter can depend on the IR without the SQL-generation code.

**`rocky-core`** holds the warehouse-agnostic logic. It depends on `rocky-ir` and knows nothing about any named warehouse or source. So a new warehouse or source needs a new adapter crate, and the core engine does not change.

## Crate overview

The 32 crates under `engine/crates/`, the two binary crates, and the browser UI:

```
engine/
├── crates/
│   ├── rocky-ir/            # Typed IR (ModelIr, MaterializationStrategy)
│   ├── rocky-core/          # Generic SQL transformation engine
│   ├── rocky-secret-registry/  # Prints resolved ${VAR} values as ${NAME}
│   ├── rocky-core-compiletest/  # Compile-fail (trybuild) guards for rocky-core
│   ├── rocky-cli-compiletest/   # Compile-fail guard: rocky-cli's plan writers stay crate-private
│   ├── rocky-catalog-core/  # Catalog client abstraction (Iceberg REST, Unity Catalog, Polaris, Nessie)
│   ├── rocky-sql/           # SQL parsing + typed AST
│   ├── rocky-lang/          # Rocky DSL parser (.rocky files)
│   ├── rocky-compiler/      # Type checking + semantic analysis
│   ├── rocky-adapter-sdk/   # Adapter SDK + conformance tests
│   ├── rocky-databricks/ rocky-snowflake/ rocky-bigquery/ rocky-trino/
│   ├── rocky-postgres/ rocky-sqlserver/ rocky-clickhouse/ rocky-spark/
│   ├── rocky-fivetran/ rocky-airbyte/ rocky-iceberg/ rocky-duckdb/
│   ├── rocky-engine/        # Local execution engine (DuckDB-backed)
│   ├── rocky-server/        # HTTP server support (auth, jobs, UI guard) + LSP server
│   ├── rocky-cache/         # Three-tier caching
│   ├── rocky-ai/            # AI intent layer
│   ├── rocky-fulfill/       # Fulfillment loop behind `rocky fulfill` (experimental)
│   ├── rocky-mcp/           # MCP server backing `rocky mcp`
│   ├── rocky-verify/        # Standalone offline verifier for rocky-manifest attestations
│   ├── rocky-observe/       # Observability
│   ├── rocky-wasm/          # WebAssembly exports for browser/edge
│   └── rocky-cli/           # CLI framework, `/api/v1` routes, Dagster Pipes
├── rocky/                   # Binary crate (the `rocky` CLI)
├── rocky-lsp/               # Binary crate (the `rocky lsp` language server)
└── ui/                      # Browser UI (React), embedded by `rocky serve --ui`
```

### rocky-ir

The typed IR. It carries data only: no traits, no logic. It holds `ModelIr`, the `MaterializationStrategy` enum ([below](#materializationstrategy)), the source and target descriptors, and partition windows.

### rocky-core

The warehouse-agnostic engine. It reads IR and writes SQL for one dialect.

| Module | Job |
|---|---|
| `schema.rs` | Schema pattern parsing (`src__acme__us_west__shopify` into components) |
| `drift.rs` | Schema drift detection |
| `sql_gen.rs` | IR to dialect-specific SQL |
| `state.rs` | Embedded `redb` state store: watermarks, run history |
| `state_sync.rs` | Remote state: S3, GCS, Valkey, or tiered (Valkey + S3) |
| `catalog.rs` | Catalog and schema lifecycle (CREATE IF NOT EXISTS, tagging) |
| `checks.rs`, `contracts.rs` | Inline data quality checks, data contracts |
| `unified_dag.rs`, `dag_executor.rs` | Layered execution across pipeline stages (the topological sort is in `rocky-ir::dag`) |
| `models.rs` | Model loading (sidecar `.sql` + `.toml`) |
| `source.rs` | Source adapter traits, manual source |
| `config.rs` | TOML parsing with `${VAR}` and `${VAR:-default}` substitution |

### rocky-sql

SQL parsing and validation on `sqlparser-rs`. It reads SQL. Each adapter's own `SqlDialect` writes the per-warehouse SQL.

- **parser.rs**: wraps sqlparser-rs with typed extensions.
- **dialect.rs**: the one dialect Rocky parses every model with, whatever the target warehouse. It follows Databricks SQL and accepts `SELECT * EXCEPT (...)`, `* EXCLUDE (...)` and `* REPLACE (... AS col)`. With `[portability] target_dialect` set, `P001` flags `* EXCLUDE` and `* REPLACE` on a target that lacks them.
- **validation.rs**: identifier validation. Every identifier must match `^[a-zA-Z0-9_]+$` before it enters SQL. See [SQL Safety](/concepts/sql-generation/#sql-safety).

### rocky-databricks

The Databricks adapter: the SQL Statement Execution REST API (`POST /api/2.0/sql/statements`, polling), Unity Catalog CRUD and tagging, workspace bindings for catalog isolation, and batched `information_schema` queries (UNION ALL, batches of 200). `permissions.rs` runs GRANT and parses SHOW GRANTS. REVOKE helpers exist, but `rocky run` does not call them. Auth tries PAT (`DATABRICKS_TOKEN`), then OAuth M2M (`DATABRICKS_CLIENT_ID` + `DATABRICKS_CLIENT_SECRET`).

### rocky-fivetran

The Fivetran source adapter. Discovery is metadata only: a cursor-paginated REST client (Basic Auth) lists connectors and their schemas, and `sync.rs` detects new data by timestamp comparison.

### rocky-cache

Three-tier cache that cuts API calls: in-process LRU with TTL, Valkey/Redis with distributed locks, and a tiered chain (memory, then Valkey, then API). A miss at one tier fills the tiers above it.

### rocky-observe

- **metrics.rs**: counters (tables processed and failed, statements, retries, anomalies) and duration histograms (p50, p95, max). Atomics; serialized into run output.
- **tracing_setup.rs**: structured JSON logging (`tracing`)
- **events.rs**: event broadcast over Valkey Pub/Sub
- **otel.rs**: OpenTelemetry exporter. With `--features otel` and `OTEL_EXPORTER_OTLP_ENDPOINT` set, `rocky run` exports metrics as OTLP through an `OtelGuard`. Any OTLP collector works (Honeycomb, Datadog, Grafana Tempo, Prometheus via the OTel collector).

### rocky-lang

The DSL parser for `.rocky` files: `token.rs` (scanner, `logos`), `parser.rs` (recursive descent, typed AST), `lower.rs` (`lower_to_sql()`). The model then takes the same path as hand-written SQL.

### rocky-compiler

Type checking and semantic analysis: `typecheck.rs` (column-level type inference across the DAG), `semantic.rs` (lineage, dependencies, contracts), `diagnostic.rs` (errors and warnings with locations and suggestions). See [The Rocky Compiler](/concepts/compiler/).

### rocky-adapter-sdk

Stable, versioned traits for custom warehouse adapters:

- **`WarehouseAdapter`**: execute SQL, describe tables, manage catalog objects
- **`SqlDialect`**: format SQL for one warehouse
- **`DiscoveryAdapter`**: discover connectors and tables
- **`GovernanceAdapter`**: tags, grants, workspace bindings

It includes 26 conformance tests (18 always-run, 8 capability-gated).

### rocky-snowflake

OAuth, password and RS256 key-pair JWT auth (auto-detected), a REST client, and a dialect with dynamic tables and multi-statement transactions.

### rocky-trino

Trino adapter (Beta).

- **connector.rs**: drives `POST /v1/statement` and the `nextUri` polling state machine. Every `nextUri` must match the coordinator's scheme, host and port.
- **dialect.rs**: double-quoted identifiers, three-part names, `DESCRIBE <table>`, ANSI `INSERT INTO` / `CREATE TABLE AS`, `TABLESAMPLE BERNOULLI`.
- **auth.rs**: HTTP Basic and JWT bearer, with `RedactedString` credentials.
- **adapter.rs**: the `WarehouseAdapter` implementation.

`cargo test -p rocky-trino --features trino-conformance -- --ignored` runs the adapter against a real `trinodb/trino` coordinator in Docker. The default `cargo test -p rocky-trino` needs no credentials or network.

v0 limits: no MERGE (connector-dependent), no OAuth/Kerberos, no governance, no checksum-bisection.

### rocky-iceberg

The Iceberg and Delta UniForm writer behind the `content_addressed` strategy.

- `discover()` reads the bootstrap Delta commit: schema, partition spec, rowTracking config.
- `write_batch()` writes blake3-named Parquet files and a Delta log commit.
- `sync_iceberg_metadata()` keeps Iceberg readers in sync after each commit.

See [Content-Addressed Materialization](/concepts/content-addressed/).

### rocky-engine

Local execution engine on DuckDB (`rocky-duckdb`). It powers `rocky test`, branching, and local CI runs.

### rocky-server

- **HTTP support** (`axum`): bearer-token auth and scope, the async job model, webhook ingress, the browser UI's `Host`/`Origin` guard. The `/api/v1` routes and the embedded UI files live in `rocky-cli` (`api.rs`).
- **LSP** (`tower-lsp`): diagnostics, hover, completion, go-to-definition, rename for `rocky lsp`.

### rocky-ai

The AI intent layer (Claude): model generation, intent extraction, schema change sync, test generation. It runs the compile-verify loop (up to 3 attempts) and needs `ANTHROPIC_API_KEY`.

### rocky-cli

CLI framework on `clap`.

- **commands/**: 80+ commands by category
- **output.rs**: typed JSON output structs (80+ schemas) with `JsonSchema` for codegen
- **pipes.rs**: Dagster Pipes emitter (active when `DAGSTER_PIPES_CONTEXT` is set)

### rocky (binary)

`main.rs` wires the library crates together and dispatches CLI commands.

## Intermediate Representation (IR)

Rocky compiles your config and SQL into one typed intermediate representation
before it writes any executable SQL. Types, lineage, and validation all live on
that representation, so every later stage reads structure rather than re-parsing
text. The IR lives in the [`rocky-ir`](#rocky-ir) crate.

Two front ends feed it, and they converge before the IR:

```
  .rocky DSL ──► lower_to_sql() ──┐
  (rocky-lang/lower.rs)           │
                                  ├──► SQL string + sidecar TOML
  raw .sql + .toml sidecar ───────┘             │
                                                │ to_model_ir()
                                                │ (rocky-core/models.rs)
                                                ▼
                                            ModelIr
                                   the one typed intermediate
                                                │ sql_gen.rs
                                                ▼
                                          dialect SQL
```

There is no second intermediate form between them. A `.rocky` model and a raw-SQL
model both arrive at the IR as a SQL string plus its sidecar config. The DSL is a
front end onto SQL, never a replacement for it.

### ModelIr

`ModelIr` is the single in-memory plan representation.

`ModelIr` carries the source and target descriptors, the materialization strategy, and whatever dependencies, sources, contracts, and checks the model declares. Replication and transformation pipelines compile to the same `ModelIr` shape. Which descriptors are populated is what tells the two kinds apart.

### MaterializationStrategy

The enum decides how a model's rows land in the target table. One strategy per model. [SQL Generation](/concepts/sql-generation/) shows the statements.

| Strategy | Behavior |
|---|---|
| `FullRefresh` | Rebuilds the whole table every run |
| `Incremental` | Inserts rows newer than the watermark. The state store supplies the watermark at SQL-generation time, so recipe-hash inputs stay free of runtime state |
| `Merge` | Upserts on a unique key |
| `View` | No storage. Every read re-runs the `SELECT`. Every warehouse supports it |
| `MaterializedView` | Databricks, Snowflake and BigQuery. PostgreSQL and Redshift drop and re-create the view. Other warehouses refuse it |
| `DynamicTable` | Snowflake only, with `TARGET_LAG` |
| `TimeInterval` | Partition-keyed. `@start_date` and `@end_date` in the model SQL take per-partition timestamps. Flags: `--partition`, `--from/--to`, `--latest`, `--missing` |
| `DeleteInsert` | Deletes rows matching the partition key, then inserts. Cheaper than `Merge` when the key identifies the rewritten rows |
| `Microbatch` | Alias for `TimeInterval` with `hour` granularity (dbt-compatible name) |
| `Ephemeral` | Never materialized. The compiler inlines its SQL as a CTE in each reader |
| `Snapshot` | SCD Type 2 history. Each run closes changed versions and inserts new ones |
| `ContentAddressed` | Content-addressed Parquet plus a Delta log commit, written by `rocky-iceberg` for cross-engine reads. SQL generation does not run. See [Content-Addressed Materialization](/concepts/content-addressed/) |

The enum lives in `rocky-ir::ir::MaterializationStrategy`. SQL generation lives in `rocky-core::sql_gen`.

### Adapter SDK

The [`rocky-adapter-sdk`](#rocky-adapter-sdk) crate holds the stable, versioned traits: `WarehouseAdapter`, `SqlDialect`, `DiscoveryAdapter`, and `GovernanceAdapter`. Each adapter ships an `AdapterManifest` declaring which optional features it supports.

Write an adapter in Rust by implementing the traits directly. Write one in any other language through the **process adapter protocol**: JSON-RPC over stdio.

Scaffold a new adapter:
```bash
rocky init-adapter bigquery
```

Run conformance tests:
```bash
rocky test-adapter --adapter duckdb
```
